# Y-Statement ADR

Создавай ADR по описанию архитектурного решения.

## Порядок работы

1. Выдели из источника шесть частей Y-Statement.
2. Если данных для части нет, поставь `—`. Ничего не выдумывай.
3. Сформируй ADR.
4. Если есть прочерки, после Y-Statement добавь `## Задачи на доработку` с одной задачей на каждый прочерк.
5. Если прочерков нет, секцию задач не добавляй.

## Формат

Используй `assets/adr-template.md` как точную структуру ADR.

- Не меняй структуру шаблона.
- Заполняй шаблон только сведениями из источника или `—`.
- Если есть пропуски, в `{tasks_section}` добавь `## Задачи на доработку` с одной задачей на каждый пропуск.
- Если пропусков нет, `{tasks_section}` оставь пустым.

## Правила

- Y-Statement — одно предложение.
- Порядок маркеров фиксирован.
- Используй только сведения из источника.
- Каждый пропуск обозначай `—`.
- Каждому `—` соответствует одна задача.
- При полном Y-Statement секции задач нет.
- Не добавляй Status, Context и Consequences.

## Сохранение ADR в файл

После формирования ADR сохрани его в проекте:

1. Используй каталог `adr/` относительно корня текущего проекта. Если его нет, создай его. Не выбирай другой каталог автоматически.
2. Получи следующий свободный номер командой `python <skill_dir>/scripts/next-adr-number.py adr/`, где `<skill_dir>` — абсолютный путь к каталогу этого навыка. Запускай команду из корня проекта. Не назначай номер вручную.
3. Сформируй `slug` по краткому названию принятого решения: латинские буквы в нижнем регистре, цифры и дефисы (`kebab-case`); кириллицу транслитерируй в латиницу; пробелы и разделители замени дефисами. Если название невозможно извлечь, используй `unspecified-decision` без выдумывания решения.
4. Замени `ADR-NNNN` в заголовке фактическим четырёхзначным номером и сохрани документ в `adr/adr-NNNN-{slug}.md`, например `adr/adr-0001-transactional-outbox.md`. Номер в заголовке и имени файла должен совпадать.
5. Не перезаписывай существующий ADR. Если имя уже занято, повторно получи свободный номер и используй его.
6. Сообщи пользователю фактический путь к созданному файлу. Не утверждай, что файл сохранён, если запись в проект недоступна; в таком случае выведи содержимое ADR и сообщи, что сохранить его не удалось.

При неполных исходных данных сохраняй черновик с `—` и задачами на доработку: отсутствие частей Y-Statement не препятствует созданию файла.

## Проверка перед сохранением

Перед записью файла открой `references/validation-checklist.md` из каталога навыка и выполни все пункты чек-листа.

- Исправляй ошибки структуры, порядка маркеров и оформления до сохранения ADR.
- Не исправляй пробелы в исходных данных выдуманными фактами: оставляй `—` и соответствующие задачи.
- Если проверка выявила проблему, которую невозможно устранить без дополнительных сведений, сохрани допустимый черновик и явно сообщи о неопределённости.
- Не объявляй проверку успешной, если соответствующий пункт не был проверен.

## Протоколирование

После создания ADR дописывай запись в `trace.md` в **корне проекта**, не затирая прежние записи. Если файла нет, создай его с заголовком `# Y-Statement skill trace`.

Для каждого ADR записывай:

```markdown
## {ISO-8601} | y-statement | ADR-NNNN

### Source
{исходный запрос и существенные уточнения пользователя}

### Reasoning
{доступный из модели или runtime reasoning trace; если он недоступен — подробное объяснение выбора формулировок на основе источника}

### Mapping
- В контексте: PRESENT | MISSING
- сталкиваясь с: PRESENT | MISSING
- мы решили: PRESENT | MISSING
- и отвергли: PRESENT | MISSING
- чтобы: PRESENT | MISSING
- принимая: PRESENT | MISSING

### Validation
PASS | FIXED | NOT_VERIFIABLE
{краткие результаты проверки и исправления}

### Output
{фактический путь к сохранённому ADR}
```

- Если открытая модель или runtime предоставляет полный reasoning trace, сохраняй **фактически доступный** trace без сокращений. Не выдумывай недоступные внутренние рассуждения.
- Если reasoning trace не предоставляется, запиши подробное объяснение: какие сведения источника сопоставлены каждой части Y-Statement, что оставлено неизвестным и почему.
- `PASS` означает, что чек-лист пройден без исправлений; `FIXED` — что ошибки формы исправлены до сохранения; `NOT_VERIFIABLE` — что проверку выполнить не удалось.
- Если `trace.md` недоступен для записи, сообщи об этом пользователю; не утверждай, что протокол создан.
- Протокол — отдельный файл: не добавляй его содержимое в ADR.
